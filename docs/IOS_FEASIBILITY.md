## 1. Как читать документ и достоверность данных

**Градация статусов:** ✅ работает официально; ⚠️ только обходной путь или есть оговорки; ❌ невозможно (официально).

**Градация достоверности (колонка «Основание»):**

| Метка | Значение |
|---|---|
| **[DOC]** | Прямо описано в документации Apple или тексте Review Guidelines |
| **[DOC*]** | Следует из документации Apple, но формулировка на момент написания по памяти (перечитать перед решением) |
| **[REPORT]** | Сообщения разработчиков (форумы, issue-трекеры, статьи). Не гарантия, зависит от версии iOS |
| **[DEVICE]** | Нельзя утверждать без прототипа на реальном устройстве. Идёт в чек-лист спайков (раздел 6) |

**Единственный факт, перепроверенный по первоисточнику при написании:** текст Guidelines 4.4.1, 2.5.1, 2.5.4, 2.5.14, 5.1.1 (страница App Store Review Guidelines, дата проверки 2026-11-04). Остальные API-утверждения сделаны по документации и опыту и обязаны пройти спайки. Симулятор для проверки не годится: микрофон, память расширений, Full Access, аудио-сессии и поведение чужих приложений проверяются **только на физических устройствах** (минимум: самый старый iPhone с iOS 17 и новый с последней iOS).

## 2. Ключевой вывод для ТЗ

Три факта меняют архитектуру `SPEC.md` сильнее остальных:

1. **Guideline 4.4.1 прямо запрещает клавиатуре «Launch other apps besides Settings»** и требует «Remain functional without full network access and without requiring full access» [DOC]. Сценарий 4A (тап на микрофон → прыжок в контейнер) нарушает первый пункт буквально. В `SPEC.md` (9.7, R-01) это подано как «средний риск, номера пунктов не фиксированы». Это не средний риск, а прямое противоречие тексту правила. Прыжок нельзя делать единственным путём голоса в MVP.
2. **Без Full Access недоступно почти всё, на чём построен ТЗ:** сеть, общий контейнер App Group, чтение общего буфера, (вероятно) общий Keychain-доступ [DOC*/DEVICE]. «Шаблоны работают без Full Access» (ТЗ 4C, S8, FR-24) верно только если встроенные шаблоны лежат в бандле расширения, а не в App Group.
3. **Системная диктовка может остаться доступной рядом с клавиатурой** (кнопка микрофона в системной нижней панели на iPhone с Face ID, `hasDictationKey`) [DEVICE]. Если подтвердится, «голос» можно сделать без выхода из клавиатуры: продиктовать в поле, затем нажать «Сделать деловым» (Rewrite с интентом). Это самый дешёвый по риску путь, и в ТЗ его нет.

## 4. Подробный разбор

### 4.1 Постоянная кнопка над клавиатурой (строка 1)

- **Факт [DOC]:** `inputAccessoryView` и `inputView` настраиваются только владельцем текстового поля, то есть своим приложением. Сторонний код не может добавить панель к **системной** клавиатуре другого приложения.
- **Единственный публичный способ встроиться в чужое поле:** Custom Keyboard. Пользователь включает её в Настройках и выбирает глобусом (или долгим нажатием на глобус).
- **Ограничения, которых нет в ТЗ:**
  - В защищённых полях (пароль, `isSecureTextEntry`) и в цифровых/телефонных раскладках система подменяет сторонние клавиатуры системной [DOC*]. Для YAY это значит: в таких полях панели не будет. Ожидаемо, но нужно в онбординге.
  - Приложение-хост может запретить сторонние клавиатуры (`application(_:shouldAllowExtensionPointIdentifier:)`). Типично для банков; для WhatsApp/Telegram/iMessage/Mail не ожидается, проверить в матрице приложений [DEVICE].
  - Пользователь должен каждый раз переключаться глобусом на YAY. iOS запоминает последнюю клавиатуру, но не гарантирует. Это главное трение продукта и его надо мерить (метрика «доля сессий, где YAY уже была активна»).
  - Высота: задаётся констрейнтом на `view`; рисовать за пределами области клавиатуры нельзя. Высоты из ТЗ 5.1 разумны, но верхний предел определяет система [DEVICE].
- **Обязательное для ревью [DOC, 4.4.1]:** кнопка перехода на следующую клавиатуру (`advanceToNextInputMode()` / `handleInputModeList(from:with:)`, показывать по `needsInputModeSwitchKey`) и **функциональность ввода символов** («Provide keyboard input functionality»). Панель без раскладки не пройдёт.
- **Решение:** ✅ как в ТЗ (панель + компактная раскладка). Риск: Apple может счесть «клавиатуру-обёртку над ИИ» недостаточной по пункту «keyboard input functionality»; раскладка he/ru/en нужна полноценной, а не декоративной.

### 4.2 Микрофон (строка 2)

- **Факт [DOC]:** в документации Apple по Custom Keyboards сказано, что у клавиатуры нет доступа к микрофону, поэтому диктовка в самой клавиатуре невозможна. Запрос `AVAudioSession.requestRecordPermission` из расширения бесполезен.
- **Что остаётся:**
  1. Запись в контейнере (нужен переход, см. раздел 5).
  2. **Системная диктовка.** `UIInputViewController.hasDictationKey` [DOC*]; на iPhone с Face ID система показывает кнопку диктовки в нижней панели под клавиатурой. Появляется ли она у стороннего расширения и работает ли с ивритом/русским, **не проверено** [DEVICE]. Спайк S-4.
  3. App Intents/Shortcuts/Action Button/Back Tap запускают запись **вне клавиатуры** (v2 в ТЗ, но по риску это самый чистый путь).
  4. **iOS 18+: `AudioRecordingIntent`** (App Intents) позволяет начать запись из системной точки входа (Control Center, Action Button) с обязательной Live Activity-индикацией [DOC*]. Это официальный способ записи без выхода на передний план контейнера. Требует iOS 18, то есть выше минимума ТЗ (iOS 17+). Спайк S-5.
- **Распознавание:** `SFSpeechRecognizer` для `he-IL` — наличие on-device режима (`supportsOnDeviceRecognition`) по устройствам не подтверждено [DEVICE] (O-03 в ТЗ). Серверный режим Apple ограничен по длительности (порядка минуты на запрос) [DOC*]. На новых iOS есть более новые API распознавания (`SpeechAnalyzer` и родственные); поддержку иврита проверить [DEVICE].
- **Альтернатива без Apple STT:** отправлять аудио мультимодальной модели через OpenRouter (если модель принимает аудио; проверить в документации OpenRouter). Плюс: лучшее понимание намерения и иврита. Минус: аудио покидает устройство, меняет таблицу приватности ТЗ 9.2 и метки App Store. Только как опция v1.
- **Риск App Review:** 2.5.14 требует явного согласия и **явной индикации записи** [DOC]. 5.1.1(iii) — запрашивать только релевантные данные [DOC].

### 4.3 Чтение истории чата и входящего сообщения (строки 3–4)

- **Факт [DOC]:** `textDocumentProxy` отдаёт только `documentContextBeforeInput`, `documentContextAfterInput`, `selectedText` текущего поля. Это не переписка. Длина контекста ограничена (обычно текущий абзац или часть текста, не весь документ) [REPORT]. Значения могут быть `nil` (пустое поле, кастомные поля, веб-вью) [DEVICE].
- **Буфер обмена:**
  - Чтение `UIPasteboard.general` из клавиатуры возможно только при Full Access [DOC*].
  - С iOS 16 при программном чтении чужого содержимого система показывает запрос «Разрешить вставку» (или баннер) [DOC*]. Как это ведёт себя именно в расширении клавиатуры с Full Access — **не подтверждено** (O-07 в ТЗ) [DEVICE].
  - **`UIPasteControl`** (iOS 16+) — системная кнопка, чтение по её нажатию не вызывает запрос [DOC*]. Работает ли она в расширении клавиатуры, и как стилизуется, проверить [DEVICE]. Если да, это лучший способ получить сообщение клиента: чип «Вставить сообщение клиента» в панели.
  - `UIPasteboard.general.hasStrings` и `detectPatterns` не читают содержимое, их можно использовать для подсвечивания чипа без запроса [DOC*].
  - Пользовательская настройка iOS «Вставка из других приложений» (Разрешить / Спрашивать / Не разрешать) задаётся для приложения YAY; предложить «Разрешить» в онбординге [DEVICE].
- **Share Extension** — легальный, но вне поля ввода: пользователь выделяет текст → «Поделиться» → YAY. Нужен лишний шаг, зато не требует буфера и Full Access у контейнера.
- **Скриншот и OCR (Vision)** — только v2 по ТЗ; потребует отдельного согласия.
- **Автораспознавание клиента по тексту** не должно подменять выбор пользователя (ТЗ FR-29 верно).
- **Рекомендация:** ✅/⚠️: контекст из `selectedText` и `UIPasteControl`; буфер без этой кнопки — по тапу, как в ТЗ FR-08, с проверкой баннера.

### 4.4 Вставка и замена текста (строка 5)

- **API [DOC]:** `insertText(_:)`, `deleteBackward()`, `adjustTextPosition(byCharacterOffset:)`, `hasText`, `documentIdentifier`, `documentInputMode`. Отката (undo) в proxy нет.
- **Замена выделения:** `deleteBackward()` при выделении обычно удаляет выделение [DEVICE]. Если выделения нет: сдвинуть курсор в конец (`adjustTextPosition` на длину `documentContextAfterInput`), затем `deleteBackward()` N раз по длине `documentContextBeforeInput`. Для 2000 символов это 2000 вызовов; скорость и устойчивость проверить в WhatsApp, Telegram, iMessage, Mail, Notes [DEVICE].
- **Подводные камни:** некоторые поля обрабатывают вставку по символам (автокоррекция, превью ссылок); смешанный RTL/LTR текст требует проверки порядка символов и пробелов; эмодзи и суррогатные пары в `deleteBackward`.
- **Рекомендация:** ✅. Всегда сохранять исходный текст в черновик перед заменой (отката нет).

### 4.5 «Вставить и отправить» (строка 6)

- **Факт:** у расширения нет доступа к кнопке Send чужого приложения. `insertText("\n")` равен нажатию Return: в WhatsApp, iMessage, Telegram на iOS Return вставляет перенос строки, а не отправляет, а в некоторых веб-полях может отправить (непредсказуемо) [DEVICE].
- **Правила [DOC, 4.4.1]:** клавиатура не должна «Repurpose keyboard buttons for other behaviors». Использовать Return как «Отправить» — прямой риск.
- **Решение:** ❌, заменено подсказкой «Нажмите отправить» (FR-51). Как в ТЗ.

### 4.6 Чтение вслух (строка 7)

- В контейнере `AVSpeechSynthesizer` работает штатно [DOC]; качество he-IL голоса оценить на слух [DEVICE].
- В расширении: аудио-сессия и вывод из процесса клавиатуры — **не подтверждено**; клавиатуры проигрывают системные «щелчки» (`UIDevice.playInputClick`, `enableInputClicksWhenVisible`), но это другой механизм [DOC*]. Проверка S-6.
- Учесть физический переключатель тишины: по умолчанию синтезатор речи может молчать в режиме «без звука» (зависит от категории `AVAudioSession`) [DEVICE]. Тихий режим YAY должен быть независимым флагом.
- **Рекомендация:** ⚠️ MVP: озвучка только в контейнере (как в ТЗ FR-40). Из клавиатуры — после S-6.

### 4.7 Тихий режим (строка 8)

✅ Нет ограничений платформы. Haptics из клавиатуры (`UIImpactFeedbackGenerator`) по документации требуют Full Access [DOC*] [DEVICE], поэтому без Full Access haptics нет вообще; это нужно учесть в состоянии S8.

### 4.8 Сеть из клавиатуры (строка 9)

- **Факт [DOC]:** сеть расширению доступна только при `RequestsOpenAccess = YES` в Info.plist и включённом пользователем «Разрешить полный доступ». При включении система показывает предупреждение о том, что разработчик может получить доступ к вводимому.
- **Жизненный цикл [REPORT]/[DEVICE]:** процесс клавиатуры может быть приостановлен или убит при смене поля, приложения или закрытии клавиатуры. Запрос на 4–8 с может оборваться. Следствия: хранить состояние запроса в App Group (если доступно), повторять запрос при следующем показе, а длинные задачи выполнять в контейнере; `URLSession` с фоновой конфигурацией в расширении клавиатуры — **не проверено**.
- **App Review [DOC, 4.4.1]:** клавиатура обязана «Remain functional without full network access and without requiring full access». Это не значит «все функции без Full Access», но AI-функции должны быть **дополнением** к работающему вводу, а не единственным смыслом. Реальная трактовка Apple проявляется только на ревью; публично известно, что в App Store есть AI-клавиатуры с запросом Full Access, детали их прохождения нам неизвестны.
- **«Собирать активность только для улучшения клавиатуры» [DOC]:** отправка в OpenRouter контекста и текста поля допустима только по явному действию пользователя, нажатия клавиш не логируются и не отправляются. Это нужно записать в политику приватности и зафиксировать тестом.
- **Рекомендация:** ⚠️ как в ТЗ, плюс явный режим «без Full Access»: полноценная раскладка, шаблоны из бандла, баннер S8.

### 4.9 Keychain и App Group из расширения (строка 10)

- **Факты [DOC*]:** общий контейнер с основным приложением упоминается среди возможностей, требующих Open Access. Keychain access group технически общая, но доступ расширения без Full Access не подтверждён.
- **Что нужно проверить [DEVICE]** (матрица 2×2: Full Access вкл/выкл × чтение/запись):
  - `UserDefaults(suiteName:)` и файлы в контейнере группы;
  - чтение ключа из Keychain группы;
  - доступность после перезагрузки до первой разблокировки (O-10 в ТЗ).
- **Следствие для архитектуры, если без Full Access всё недоступно:** встроенные шаблоны и минимум настроек (язык, тихий режим) должны дублироваться в **бандле расширения**; пользовательские шаблоны без Full Access недоступны; баннер S8 должен это честно сказать.
- **Безопасность ключа:** ключ OpenRouter, считанный клавиатурой, живёт в её процессе. Не логировать, не кэшировать в расширении дольше запроса.
- **Решение:** ⚠️ + спайк S-3.

### 4.10 Лимит памяти (строка 11)

- Apple точное значение не публикует [DOC]. В сообществе встречаются оценки порядка 48–70 МБ в зависимости от устройства и версии iOS [REPORT]. SPEC.md принимает 60–70 МБ как ориентир и ≤ 60 МБ как цель: это **слишком оптимистично** для старых устройств.
- **Правило:** бюджет ≤ 40 МБ пик на самом старом поддерживаемом устройстве, без роста за 50 запросов подряд. Метрики через Instruments (Allocations, Memory Graph), а не по Xcode-индикатору.
- **Что есть риск раздуть:** SwiftUI-иерархия, шрифты иврита/кириллицы, `JSONDecoder` на больших ответах, база клиентов в памяти, анимации волны, `URLSession` буферы стриминга.
- **Решение:** ⚠️ как в ТЗ 3.3 п. 5, но с жёсткой цифрой и ранним замером (S-7).

## 5. Контейнер: открытие, возврат и фоновая аудио-сессия

Это самый рискованный блок продукта. Сначала правила, затем варианты.

### 5.1 Что говорят правила (проверено по Guidelines)

| Пункт | Текст (суть) | Следствие |
|---|---|---|
| **4.4.1** | Клавиатуры **не должны** «Launch other apps besides Settings» | Открытие контейнера из клавиатуры формально нарушает правило. Это главный риск-фактор |
| **4.4.1** | Клавиатуры **должны** оставаться функциональными без полного сетевого доступа и без требования Full Access | AI-сервис нельзя делать единственной функциональностью |
| **4.4.1** | Клавиатуры **должны** предоставлять ввод символов и переход на следующую клавиатуру | Раскладка и глобус обязательны |
| **2.5.1** | Только публичные API | Обходы через private selectors/KVC (например `_hostBundleID`) недопустимы |
| **2.5.4** | Фоновые сервисы только по назначению: VoIP, воспроизведение аудио, геолокация, task completion, локальные уведомления и т.п. | «Держать аудио-сессию, чтобы клавиатура мгновенно стартовала запись» легко трактуется как злоупотребление |
| **2.5.14** | Явное согласие и **явная индикация** записи (микрофон, экран, ввод) | Нужны согласие, индикатор, возможность остановить |
| **5.1.1** | Политика конфиденциальности, согласие, минимизация данных, уважение отказа | Голос и данные клиентов третьих лиц |

### 5.2 Способы открыть контейнер

| Способ | Статус | Основание | Риск |
|---|---|---|---|
| `extensionContext?.open(_:completionHandler:)` | ❌ для клавиатур (документирован для ограниченного набора расширений, например Today) | [DOC*] | - |
| Responder chain: найти `UIApplication` по `UIResponder.next` и вызвать `open(_:options:completionHandler:)` по селектору | ⚠️ Известный обход. На разных версиях iOS ломается или меняется (сообщения о проблемах на iOS 18 с прежним `openURL:`) | [REPORT] [DEVICE] | **Высокий**: 4.4.1 (запуск приложений), возможен вопрос по 2.5.1 |
| SwiftUI `Link` / `openURL` из клавиатуры | ⚠️ Гипотеза: в части версий может сработать | [DEVICE] | Тот же 4.4.1 |
| Universal Link (https) вместо схемы | ⚠️ Тот же механизм, но без URL scheme | [DEVICE] | Тот же 4.4.1 |
| Открыть **Настройки** (`UIApplication.openSettingsURLString`) | ✅ Правило прямо разрешает «Settings» | [DOC] | Низкий. Только для онбординга Full Access |
| Пользователь сам открывает YAY (иконка, виджет, Action Button) | ✅ | - | Нет |

**Вывод:** любой путь «клавиатура → контейнер» держится на ненадёжном или формально запрещённом механизме. Закладывать его как единственный способ голоса нельзя.

### 5.3 Возврат в предыдущее приложение

- **Официального API нет** [DOC*]. После перехода по URL система показывает в статус-баре кнопку «‹ WhatsApp» (возврат к приложению-источнику) [DEVICE]; показывается ли она при переходе, инициированном **расширением клавиатуры** (источник — хост-приложение), — спайк S-1. Устройства с Dynamic Island отображают её по-другому.
- **Автоматический возврат** через угадывание хост-приложения по приватным ключам запрещён (2.5.1). Публичные описания продуктов вроде Wispr Flow говорят о схеме «открыть приложение → начать фоновую сессию → вернуться»; как именно реализован возврат, не подтверждено, и копировать не следует.
- **Реалистичные варианты (по убыванию надёжности):**

| # | Вариант | Как работает | Статус | Комментарий |
|---|---|---|---|---|
| R1 | Системная «‹ Приложение» в статус-баре | Пользователь нажимает её после записи | ⚠️ [DEVICE] | Бесплатно, но зависит от того, покажет ли её система |
| R2 | Свайп/жест переключения приложений | Пользователь возвращается вручную; экран записи пишет «Вернитесь в WhatsApp» | ✅ | Запасной вариант в MVP (как в ТЗ) |
| R3 | **Deep link в чат клиента** из контейнера | Если у клиента сохранён номер/логин: `https://wa.me/<номер>`, `tg://resolve?domain=...`, `sms:<номер>` открывают нужный чат. Нужны `LSApplicationQueriesSchemes` для `canOpenURL` | ⚠️ [DEVICE] | Возвращает в **нужный чат**, а не в «последнее приложение». Требует номера клиента (поле в карточке; ТЗ его не содержит) и может открыть чат с пустым полем (сообщение придётся вставить из буфера) |
| R4 | Не покидать приложение: диктовка системным микрофоном | Нет перехода вообще | ⚠️ S-4 | Лучший по UX и по риску |
| R5 | Запись без выхода: `AudioRecordingIntent`, Control Center, Action Button (iOS 18+) | Запись стартует системой, контейнер на передний план не выходит | ⚠️ S-5 | Официально, но вне клавиатуры и только iOS 18+ |

### 5.4 Фоновая аудио-сессия (v1 в ТЗ, FR-03)

- **Как это должно работать [REPORT]:** контейнер с `UIBackgroundModes = audio` держит активную `AVAudioSession` (`.playAndRecord`); клавиатура будит запись Darwin-уведомлением (`CFNotificationCenterGetDarwinNotifyCenter`, без полезной нагрузки, данные через App Group); микрофон уже «разогрет», перехода не нужно.
- **Факты и неизвестные:**
  - Запуск захвата с микрофона из фона при уже активной сессии разрешён не во всех случаях и менялся между версиями iOS [REPORT]. Это критический вопрос S-2.
  - Пока микрофон «горячий», система показывает оранжевый индикатор микрофона. Постоянный индикатор в ожидании = ощущение слежки и жалобы.
  - Прерывания: звонки, Siri, запись голосового в WhatsApp, Bluetooth, другой аудиоплеер. Сессия умирает, и клавиатура не должна считать её живой без проверки состояния.
  - Jetsam контейнера при нехватке памяти; принудительное закрытие свайпом убивает сессию.
  - Батарея: нужен замер за рабочий день.
- **Риск App Review [DOC]:** 2.5.4 (аудио-режим для удержания процесса), 2.5.14 (явная индикация и согласие), 5.1.1 (прозрачность). **Высокий.**
- **Смягчение, если всё же делать:** включается пользователем явно с экраном-объяснением; сессия держит только запись **по тапу** (не слушает постоянно); таймаут по бездействию (например 2–5 минут); индикатор «Сессия активна» в приложении и Live Activity; Review Notes с описанием, как проверить.

### 5.5 Рекомендация по блоку

1. **MVP не зависит от прыжка.** Голос в MVP: системная диктовка (если S-4 успешен) + запись из контейнера через явный вход (иконка, виджет, Action Button) + результат в буфер/App Group и вставка клавиатурой.
2. Прыжок из клавиатуры — флаг, **выключенный в App Store-сборке**, пока (а) S-1 не покажет, что механизм стабилен на iOS 17/18/последней, (б) не проведена консультация по 4.4.1 (запрос в App Review через Resolution Center/pre-submission, если доступно).
3. Фоновая сессия — только v1 и только после S-2 и юридической оценки.

## 8. Рекомендация: go / no-go

**GO, с условиями.** Продукт реализуем, если переопределить голос и не опираться на прыжок.

| Часть продукта | Решение | Условие |
|---|---|---|
| Панель + раскладка + вставка | **GO** | S-3, S-7, S-9 пройдены |
| Rewrite выделенного/набранного текста | **GO** | S-9 |
| Генерация ответа по тексту/буферу в клавиатуре | **GO** | Full Access, S-8, S-11 |
| Шаблоны без Full Access | **GO** | Встроенные в бандле расширения |
| Голос через системную диктовку | **GO, если S-4 успешен** | Иначе фолбэк ниже |
| Голос: прыжок в контейнер | **NO-GO для MVP** | Только флаг; включать после S-1 и консультации |
| Фоновая сессия (стиль Wispr Flow) | **NO-GO до S-2 и юр. оценки** | Только v1 |
| «Вставить и отправить», чтение переписки | **NO-GO** | Не реализуемо |

### Планы Б

| План | Описание | Когда включаем |
|---|---|---|
| **A (основной)** | Клавиатура: Rewrite, шаблоны, генерация из выделения/`UIPasteControl`; голос — системная диктовка + intent-преобразование продиктованного текста | S-4 успешен |
| **B** | Голос вне клавиатуры: Action Button/Control Center + `AudioRecordingIntent` (iOS 18+) или App Intent с `openAppWhenRun` → результат в буфер, вставка из клавиатуры | S-4 неуспешен, S-5 успешен |
| **C** | Голос в контейнере (экран записи), клавиатура только вставляет; возврат вручную или deep link в чат (R3) | S-4 и S-5 неуспешны |
| **D** | Без Full Access: клавиатура = раскладка + шаблоны; вся генерация в контейнере и Share Extension, результат через буфер | Apple отклоняет Full Access |
| **E** | Отказ от клавиатуры: приложение + Share Extension + Shortcuts (ответ в буфер) | Apple отклоняет продукт как «клавиатуру без ввода» |

**Контрольные точки:** после недели 1 (фундамент S-3/S-7/S-9) — решение по плану A/D; после недели 2 (голосовые спайки) — решение A/B/C; до начала разработки v1 — решение по фоновой сессии.
